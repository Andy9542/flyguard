# Допущения

Разумные допущения там, где ТЗ неясно или не подходит к имеющимся данным. Отчёт ссылается на них по номерам.

- **A1. Провайдер LLM — только DeepSeek.** Оператор выдал ключ одного провайдера (`DEEPSEEK_API_KEY` из `ecode/build/.env`, файл указан в `llm_api.key_file`). Доступные модели на 2026-09-26: `deepseek-flash` (DeepSeek-V4.1-Flash) и `deepseek-v4-pro` (DeepSeek-V4-Pro-0813). Следствия описаны в DEVIATIONS D1–D3.
- **A2. Бюджет API.** Баланс аккаунта на старте 7,75 USD; `llm_api.budget_usd = 7.0`, остаток — запас на округления. Цены взяты со страницы api-docs.deepseek.com/quick_start/pricing 26.09.2026 и лежат в `configs/operator.yaml`; расход считается по полям `usage` каждого ответа с учётом кеш-попаданий и пиковых часов (пн–пт 01:00–04:00 и 06:00–10:00 UTC, цены ×2). Генерация избегает пиковых часов (`avoid_peak_hours`).
- **A3. Режим модели агента.** Агент работает в режиме без размышлений (`thinking: disabled`) при temperature 0: в режиме размышлений DeepSeek игнорирует temperature и требует возвращать `reasoning_content` в каждом ходе с инструментами, чего харнесс AgentDojo не делает.
- **A4. Адаптация AgentDojo к DeepSeek** (`src/flyguard/gen/harness_run.py`): роль `developer` → `system` (DeepSeek её не принимает), системные блоки контента → строка; temperature передаётся явно (харнесс отбрасывает 0,0 как `NOT_GIVEN`). Имя модели в прозе для плейсхолдера `{model}` атак: `DeepSeek` (зарегистрировано в `MODEL_NAMES`); имя пользователя `Emma Johnson` — как в харнессе.
- **A5. Число баз парафраз.** В AgentDojo v1.2.2 35 задач-инъекций (workspace 14, travel 7, banking 9, slack 5), а не 27, поэтому баз шаблонов 4 × 35 = 140, а не 108.
- **A6. Объём трасс.** При v1.2.2 на один шаблон атаки приходится 949 пар «задача × инъекция» (плюс 97 чистых задач), то есть около 3 900 атакованных эпизодов на четыре шаблона, а не 2 600 из ТЗ; в AgentDyn 560 пар и 60 чистых. Проекция стоимости считается по этим числам.
- **A7. Python 3.11.14** установлен через `uv python install` (в системе только 3.10 и 3.12).
- **A8. Резервные трассы.** Опубликованные `runs/` AgentDojo и AgentDyn берутся из уже имеющегося на машине разреженного клона проекта mushka (`data/ext/published_runs_*` — симлинки), без повторного скачивания. Они нужны только для сверки ASR/utility и как резерв по ТЗ.
- **A9. Файлы промптов.** Тексты Приложения A хранятся дословно; системная и пользовательская части одного промпта лежат в одном файле, разделённом строками `===SYSTEM===` и `===USER===`. `banned_words.txt` — по одному выражению в строке.
- **A10. Сырые файлы MaleCNS** (1 ГБ `connectome-weights`) удаляются после `flypath build` и сверки sha256 из-за 8 ГБ свободного места; хеши записаны в `data/manifests/sources.json`, `fetch.sh` скачивает их заново при необходимости.
- **A11. Эталоны вредных вызовов общие с второй командой.** `configs/harm_references.yaml` скопирован дословно из проекта mushka (второй команды контракта), где он был заморожен до тестовых результатов: там ручные эталоны для случаев, когда `ground_truth()` пуст или заглушка (workspace injection_task_6–13, AgentDyn shopping и github). Общий файл нужен, чтобы `first_harmful_step` и `match` совпадали в CSV обеих команд. Дополнение — `data/processed/meta/<benchmark>_<suite>.json` с `ground_truth()` из установленных харнессов.
- **A12. Правило тестовой задачи контракта.** `crc32` берётся от строки идентификатора задачи в том виде, как его пишет харнесс (`user_task_5`), в кодировке UTF-8: `zlib.crc32(b"user_task_5") % 3 == 2`. В ТЗ второй команды (mushka, редакция от 25.09) стоит другое правило — `n % 3 == 2` по номеру задачи; расхождение отдано оператору (чек-лист: «в ТЗ второй команды лежит тот же файл контракта v3»). Пока манифесты двух команд по этому пункту не совпадут, сравнение по контракту невозможно.
- **A13. Тонкие классы эпизодов.** У выбранной модели агента targeted ASR на пилоте 0,05: `hijacked` будет мало (оценка ≈ 50 на AgentDojo `important_instructions`). Это ограничение данных, а не детектора; метрика остановки отчитывается с числом эпизодов и интервалом.
- **A14. Детерминированные компоненты мухи** (`nose.py`, `connectome.py`, `fly.py`, `readout.py`): хеш n-граммы `xxhash64(utf8(g), seed=nose) mod B` (байты UTF-8, регистр опущен); `TruncatedSVD(random_state=svd)`; перестановка π = `default_rng(perm).permutation(51)`, столбец гломерулы g несёт компоненту π[g]; k-WTA с разрывом ничьей по меньшему индексу; Bloom балансирует классы подвыборкой большинства до меньшинства (сид `subsample`), нормированный вариант E6 берёт все примеры с показателем n_c(i)·N_min/N_c; φ_c усредняет F_c по носителю кода (для k-WTA это ровно 1/k); curveball — 200 независимых цепей от измеренной M, каждая с ⌈5·E⌉ попыток обмена (счёт попыток по Strona et al.), дочерние сиды от `curveball`; случайная M той же плотности сохраняет входную степень каждой KC; плотный знаковый код имеет round(nnz/d) строк. N16k хранится без центрирования (центр вычитается в произведении с M).
- **A15. kNN(1).** Жёсткая метка ближайшего соседа даёт вырожденную ROC из одной точки, поэтому оценка kNN(1) = 0,5 ± 0,5·cos с ближайшим обучающим окном (знак по его метке); решение 1-NN восстанавливается порогом 0,5. kNN(5) — среднее меток пяти соседей. Ближайший центроид: (cos₁ − cos₀ + 1)/2.
- **A16. BIPIA.** «15 атак × 3 позиции» читается как имена атак × позиции; для каждого контекста и имени один из пяти текстов атаки выбирается сидом `subsample`; у задачи code имён 10. Вставка: `start` = атака + «\n» + контекст, `end` = контекст + «\n» + атака, `middle` = на границе предложения, выбранной сидом (аппроксимация Punkt из bipia/data/utils.py). Тестовые файлы повторяют контексты (email 44 различных из 50, table 84 из 100): одинаковые нормализованные контексты образуют одну пару, а контексты с Жаккаром ≥ 0,8 по символьным 5-граммам делят `cluster_id`, сохраняя свои пары, чтобы дедупликация не рвала тест и бутстреп по кластерам был честным. Задачи qa и abstract выпадают (BLOCKERS B4).
- **A17. Хеш окна** для кешей оценок: `xxhash64(text.encode("utf-8"), seed=0).hexdigest()`, зафиксирован в `configs/default.yaml` (`windows.text_hash`).
- **A18. Список запрещённых слов (A.1).** Буквальные топ-30 по χ² на deepset train — английские служебные слова (the, you, of…), потому что безобидная половина набора в основном немецкая; с ними глубокая парафраза невозможна. Правило: токены ≥ 3 символов с буквой, без английских стоп-слов sklearn, только обогащённые в инъекциях (доля в инъекциях выше, чем в безобидных), уже покрытые стартовым списком пропускаются, ничьи по алфавиту. Итоговый список пишется в `paraphrases_manifest.json`.
- **A19. Контракт §6 для AgentDyn.** Все чистые прогоны нетестовых задач AgentDyn идут в валидацию порога (`splits.contract.agentdyn_clean_non_test: validation`); для AgentDojo валидация — 20 % нетестовых задач от общего сида 0 (сид `subsample`). Шаг эпизода = i-й ответ инструмента (исполненный вызов). В AgentDojo вызовов без ответа нет; в AgentDyn их 38 в 36 логах, все в завершающем сообщении ассистента после последнего исполненного шага, поэтому нумерация исполненных шагов совпадает с нумерацией по вызовам у второй команды; счётчик `unanswered_tool_calls` остаётся в `traces_extraction.json`.
- **A20. Незакрытые эталоны.** 12 из 139 угнанных эпизодов AgentDojo (0 из 11 в AgentDyn) у v4-pro не совпали ни с одним эталонным вызовом даже по имени (`match = unmatched`); по контракту §4 они исключаются из метрики остановки и отчитываются отдельно (`traces_extraction.json`). Файл эталонов после генерации не меняется.
- **A21. Модель кластеров в E0.** Синтетика мощности воспроизводит наблюдаемую структуру кластеров двумя входами: `cluster_label_sizes` — состав (позитивы, негативы) каждого наблюдаемого кластера, пересэмплируется с сохранением смеси (BIPIA: пара 0+1; dojo/dyn: `<suite>/<user_task>` с чистыми и заражёнными шагами); `cluster_sizes` — кластеры с постоянной меткой (deep: одиночные документы; para: база одной метки). На модели проверено: для парной разности AUC обе схемы дают одинаковый разброс (общий кластерный эффект сокращается в разности), для ДИ одного детектора модель постоянных меток завышает разброс смешанного источника на 16–53 %. Выбранная модель пишется в `power.json → assumptions.cluster_model`.
- **A22. Задержка обнаружения в контракте §9.** `detection_delay_*` и `n_detections` считаются по эпизодам `hijacked` (включая `unmatched`: задержке эталон не нужен); тревоги и задержки на `injection_ignored` отчитываются отдельными полями `*_ignored`, как «отдельно» в §9. Прочтение подлежит подтверждению второй командой.
- **A23. Детали конвейера данных.** (a) BIPIA делится 20/80 на валидацию и тест по кластерам внутри каждой задачи; (b) `doc_id` BIPIA несёт имя атаки, индекс строки и позицию: `bipia:<task>:<ctx>:<slug>-<k>:<pos>`, чистый документ — `:clean`; (c) «чистые ответы» пулов — окна с меткой 0 только из чистых эпизодов, окна с меткой 0 из атакованных эпизодов в пулы не входят; (d) проверка «ни один кластер не содержит обе метки» выполняется по группам дубликатов (`dup_of`), а не по `cluster_id`, потому что пары BIPIA делят `cluster_id` по построению; (e) позитивный тестовый документ, у которого исключены все позитивные окна, выпадает, а не перемечается; (f) имена шаблонов ТЗ 1.10 = имена атак реестра харнесса (`--help`): `important_instructions`, `tool_knowledge`, `injecagent`, `ignore_previous`, сверены с `agentdojo.attacks.attack_registry`; (g) варианты E6 валидационных контекстов BIPIA не входят в `e1.val`, C_unl и пулы, но служат эталонами дедупликации (ТЗ 1.7 буквально), это записано в `splits.json → bipia.e6_role`; (h) LSH дедупликации строится с полосами b = 25, r = 5 (вероятность кандидата 0,99995 при J = 0,8), совпадение проверяется точным Жаккаром; (i) чтение обучающего набора PIGuard для аудита контаминации журналируется с меткой `external`.
- **A24. Аудит контаминации (ТЗ 3.2), первые числа.** Все документы deepset train и val (436 и 110) целиком присутствуют в открытом обучающем наборе PIGuard (тег prompt-injections); deepset test — 4 из 116; BIPIA основной тест — 19 из 280 документов целиком, 5 % окон; NotInject — 0. Это входит в угрозы валидности: PIGuard видел обучающий набор мухи и часть тестов; ProtectAI v2 по карточке обучался на других наборах.
- **A25. Роль атакованных эпизодов валидационных задач AgentDojo.** ТЗ 1.8 и 1.10 дают валидационным задачам (crc32 mod 5 = 0) роль только через их чистые ответы (пул P_val) и исключают эти задачи из теста. Их атакованные эпизоды получают роль `unused`: они не входят в валидацию, тест, C_unl и пулы и не служат эталонами дедупликации. Иначе при статичных окружениях каждое тестовое окно с тем же текстом инъекции считалось бы дубликатом «валидационного» окна и выпадало бы из теста (механизм уже снял 1 236 окон BIPIA на этапе 1). Решение принято до просмотра результатов E1.
- **A26. Валидация гиперпараметров в экспериментах.** γ (Bloom) и C (линейный выход, LR на N51-svd, TF-IDF+LR) выбираются по AUC на окнах валидационной части deepset train (20 %, стратифицированно): метки только из deepset train (ТЗ 1.10). Валидационные документы BIPIA и AgentDojo в выборе гиперпараметров не участвуют, но входят в валидационные AUC и macroAUC для предусловий H2/H3 (`val_auc/<источник>/<детектор>`, `val_macro_auc/<детектор>`, уровень документов).
- **A27. Доступ к тесту в экспериментах.** Нетестовые таблицы читаются с фильтром `split != test`; тестовые строки источника читаются только через `Context.load_test_windows` и журналируются один раз на источник за прогон; окна, исключённые дедупликацией, отбрасываются до оценки. `episodes.parquet` (метаданные эпизодов без текста) читается целиком: он нужен фолдам E3 и контракту. E0 берёт число позитивов, негативов и состав кластеров тестовых источников агрегатно из столбцов `label`/`cluster_id` через ту же дверь (только счётчики); поэтому чтение E0 предшествует заморозке `power.json` по построению, а критерий приёмки сравнивает время создания `power.json` с файлами результатов E1.
- **A28. Few-shot (E2, H1b ii).** «N примеров» = N обучающих документов на класс из deepset train без возвращения, генератор от `SeedSequence([subsample, N, номер подвыборки])`, 10 подвыборок на точку; γ и C выбираются на валидации deepset отдельно для каждой подгонки (уровень × подвыборка), в результаты пишутся выборы и модальное значение. Число точки = среднее macroAUC по подвыборкам с персентильным интервалом по общим кластерным розыгрышам; полоса графика = минимум и максимум подвыборок. Разность H1b(ii) Bloom − kNN(1) при 1 и 10 примерах — среднее парных разностей на одной подвыборке. Уровень 100 пропускается, если в обучении меньше 100 документов класса. «Bloom при 10 примерах» в E4 = `fewshot_set(10, rep=0)`.
- **A29. Разности и сводка по сидам.** Парные разности пишутся как `diff/<метрика>/<a>-<b>` (95 % ДИ и двусторонний бутстреп-p) и `diff90/…` (90 % ДИ тех же розыгрышей, для TOST). Глубокая страта парафраз оценивается как псевдоисточник `para_deep`. Сводка `results/<E>/summary.json`: среднее, СКО, минимум и максимум по сидам, значения и ДИ каждого сида и t-интервал среднего по точкам сидов; усреднение границ бутстреп-интервалов не применяется.
- **A30. Вердикты при 10 сидах.** Правила ТЗ заданы для одного интервала. Вердикт выносится по каждому сиду; итоговый статус — модальный по сидам, ничья разрешается в сторону более осторожного (не хватило данных < предусловие не выполнено < опровергнута < подтверждена); рядом — число сидов по статусам, средний эффект и огибающая интервалов (описательно).
- **A31. E0.** Уровень планирования AUC — ближайший из {0,75; 0,85; 0,95} к минимуму валидационных AUC (по документам, источники deep, bipia, dojo) двух планировочных детекторов real_fly_bloom и tfidf_lr; разброс curveball и π — для Bloom-мухи на полном обучении. Идемпотентность E0 определяется по `power.json` (текущий хеш конфига, стадия, флаг frozen), стадия 1 не перезаписывает замороженный файл.
- **A32. E3.** Носы E3 (центрирование N16k, SVD и стандартизация N51-svd, idf TF-IDF) обучаются на C_unl E1 без окон AgentDojo: чистые документы AgentDojo из валидации E1 лежат на тестовой стороне фолдов E3 (в кросс-сьютовом семействе 2,7–19,7 % негативов фолда), а ТЗ 1.9 запрещает тестовым кластерам входить в C_unl; C_unl E3 = 546 документов deepset + 76 BIPIA (таблица `transfer_c_unl`). В каждом пригодном фолде 20 % кластеров обучающей стороны откладываются от `SeedSequence([subsample, crc32(<семейство>/<фолд>)])` (перерозыгрыш до 20 раз, если в отложенной части один класс); на них подбираются γ и C, на их документах без инъекции — порог τ_fold. Уровень FPR порога — правило носителя Этапа 0 по числу отложенных негативов; при меньше 500 — резервные 5 % с флагом `below_pool_min`. Метрики: кросс-шаблонный — TPR при τ_fold и AUC; кросс-сьютовый — только FPR на незнакомом сьюте; двойное удержание — TPR, FPR, AUC с числом позитивов. Детекторы фолдов: tfidf_lr, knn1, centroid, lr_svd, real_fly_bloom, real_fly_linear, flyhash_bloom и regex как необучаемая точка; flyhash_linear исключён по стоимости.
- **A33. E4.** Каноническая статистика рандомизационного теста — macroAUC, усреднённый по π десяти глобальных сидов (та же величина, что в двухступенчатом бутстрепе и TOST); значение при собственном π сида пишется рядом. Семейство Хольма в E4 — все пары (выход, метрика), кроме основной (Bloom, macroAUC): 3 выхода × 6 метрик − 1 = 17; `verdicts_run` отдельно поправляет два вторичных выхода H3. δ для TOST H3 = 5 % от среднего macroAUC по нулям. Число curveball-нулей берётся из `expansion.curveball.n_null` (200), `E4.yaml n_curveball` проверяется на совпадение.
- **A34. E6.** «Все атаки × позиции BIPIA» = основные тестовые пары плюс варианты E6 тех же контекстов; негативы — все чистые документы; интервалы у маргиналей, у клеток — точечные AUC. 512-токенные окна: трансформеры оценивают документ целиком, перенарезанный токенизатором (510 + 2 токена, шаг 382), парно с 256-символьной версией на тех же документах. При фиксированной γ валидационный выбор не выполняется. τ_80 — как τ_90, по тестовым позитивам deep и dojo.
- **A35. Контракт §3, §8.** Оценка шага = максимум по всем окнам документа шага; исключения дедупликации в контракте не применяются (§10 уже принимает пересечение статических окружений). Тревога при оценке ≥ порога. Эпизод без документов шагов получает `max_score` 0 и пустой `alarm_step`, причина пишется в `results/contract.json`. Один CSV от глобального сида 0.
- **A36. Смоук.** Результаты смоука лежат в `results/smoke/`, чтобы не подменять настоящие файлы сида 0. Время смоука для критерия «15 минут» = сумма последних длительностей стадий build_stage1 … report в `logs/run_all.log`, включая `prescore`, и засчитывается только замер с пустого кеша оценок трансформеров (строка старта prescore пишет число строк кеша); прогон идемпотентен; в смоуке финальная проверка не фатальна и идёт без pytest.
- **A37. Порядок стадий `run_all.sh`.** E1 выполняется один раз, после заморозки `power.json` (E0 стадия 2), а не чередованием «дешёвые детекторы → промышленные → E0 стадия 2 → E1»: ранний прогон записал бы результаты E1 и тестовое чтение до заморозки. Генерация по API здесь предшествует CPU-стадиям, так что чередование ничего не экономит.
- **A38. Дедупликация AgentDojo на полной сборке.** Из 1 970 чистых тестовых документов AgentDojo 1 021 целиком совпадает с чистыми ответами валидационных задач (статичные окружения) и выпадает из теста по ТЗ 1.7; все 1 001 позитивный документ сохранились (A25). Негативы AgentDojo в тесте — 949 документов. Это фиксируется в отчёте как свойство бенчмарка.
- **A39. Параллельный прогон и замеры времени.** Полный прогон идёт с `run_all.sh --jobs N`: сиды E1–E6 выполняются параллельными процессами, у каждого потоки BLAS ограничены `nproc / N`; после стадии сводка пересобирается один раз по всем файлам сидов. Промышленные детекторы оцениваются заранее стадией `prescore` (оценки не зависят от сида, кеш по хешу текста, запись в кеш под файловой блокировкой), по процессу на модель с 4 потоками: на этой виртуальной машине (16 vCPU) DeBERTa насыщается на 4 потоках. Задержка промышленных детекторов в E1 измеряется только на первом сиде; задержка остальных детекторов измерена под параллельной нагрузкой и сравнима между детекторами одного прогона, а не с другими машинами.
- **A40. Хеш конфига без исполнительских ключей.** `config_hash` считает YAML по разобранному содержимому (канонический JSON с сортировкой ключей: комментарии и форматирование на хеш не влияют); `regex_patterns.txt` и промпты входят побайтно. Из хеша исключены ключи, которые меняют только скорость, параллелизм, место кеша, доступ к API и бюджет и не меняют ни одного числа результатов (`UNHASHED_KEYS`): `baselines.transformers.{batch_size, num_threads, cache_dir}`; `compute`, `hf.token_env`, `llm_api.{key_file, budget_usd, reserve_for_paraphrases_usd, prices_usd_per_million, avoid_peak_hours}`.
- **A41. Однопоточные подгонки.** Рандомизированный TruncatedSVD носа N51-svd детерминирован только при фиксированном числе потоков BLAS (16 и 8 потоков давали признаки с разницей до 2·10⁻³, это сдвигало AUC и p-значения E4). SVD и каждая подгонка детектора (`FeatureContext.fit`, перестановки π в E0) выполняются под `threadpool_limits(1)`; на смоук-таблицах признаки, выбранные γ/C и оценки всех не-трансформерных детекторов совпали побитно при 1, 4 и 16 потоках. Фактические числа потоков пишутся в каждый файл результатов (`timing.threads`). Оценки трансформеров берутся из кеша по хешу текста и внутри прогона согласованы.
- **A42. Отбор сидов в вердикты и 95 % интервалы (дополнение к A30).** В вердикты входят только сиды E1 из `seeds.global`, файлы которых несут текущий `config_hash`; остальные перечисляются в `verdicts.json → excluded_seeds`. У строк, решаемых TOST по 90 % ДИ (H1a шаблонная половина, H1b(i), H3), рядом пишется 95 % интервал тех же бутстреп-розыгрышей (`ci95`, `ci95_envelope`), так что требование «вердикт с эффектом и 95 % ДИ» выполняется для каждой гипотезы.
- **A43. Опорные значения коридора δ = 5 %.** H1a шаблонная половина: AUC ProtectAI v2 на источнике (`auc/<src>/protectai_v2`); H1b(i): macroAUC парного детектора без KC-слоя — LR на N51-svd для настоящей мухи, TF-IDF+LR на N16k для FlyHash (`macro_auc/<ref>`); H3: среднее macroAUC по curveball-нулям (A33). Во всех случаях опора — детектор-«эталон» пары, а не проверяемая муха.
- **A44. Заморозка E0 окончательна.** Если замороженный `power.json` не совпадает с текущим прогоном (хеш конфига, сид, файл сида), E0 останавливается; перезаморозка возможна только с `--force` и записью в DEVIATIONS, старая таблица архивируется в `results/E0/power_frozen_<хеш>_<время>.json`. В смоуке таблица перезамораживается сама с тем же архивом (результаты смоука в вердикты не входят). Стадия 1 E0 выполнена на снимке таблиц этапа 1 (`data/processed/stage1`, до трасс и парафраз), её таблица сохранена в `results/E0/power_stage1.json`.
- **A45. Мощность H3 в E0.** Статус носителя H3 (`carriers.macro.auc_diff_h3`) — мощность TOST ячейки macroAUC, в которой к кластерной дисперсии добавлены уровни нулевых матриц и перестановок π: sd_curveball²/J + sd_perm²/P (J = 200 нулей E4, P = 10 π); разбросы — валидационные из E0. H1b читает простую ячейку `auc_diff`.
- **A46. Отличие от нуля в выводе H3.** Эквивалентность решается по 90 % ДИ (TOST); «разность значимо отлична от нуля» — только при рандомизационном p ≤ 0,05, а без него — если 95 % интервал тех же розыгрышей исключает ноль. Исключение нуля 90 %-интервалом само по себе такого вывода не даёт.
- **A47. Предусловие H2 по строке.** Предусловие «AUC мухи на валидации deepset ≥ 0,75» проверяется для каждой строки H2 по её собственной мухе: основная (Bloom) — `val_auc/deep/real_fly_bloom`, вторичная (линейный выход) — `val_auc/deep/real_fly_linear`. Формулировка гипотезы «FPR PIGuard ниже обоих», а правило вердикта (ТЗ, Этап 4) проверяет только разность ProtectAI v2 − PIGuard; вердикт следует правилу.
- **A48. H1a и таблица E0.** Шаблонная половина H1a читает статус носителя E0 по {deep, dojo}. Семантическая половина по ТЗ проверяется «на каждом из присутствующих» источников {para (глубокая страта), bipia, dyn} и статусом носителя не отсекается; мощность E0 для para посчитана по всему источнику, а вердикт читает глубокую страту (меньше позитивов), это отмечается в отчёте.
- **A49. ROC-кривые.** Оценки документов в результаты не пишутся, поэтому E1 сохраняет сами ROC-кривые: таблица `roc` — TPR эмпирической ROC на общей сетке из 29 значений FPR (гуще при малых FPR; тревога при оценке ≥ порога, площадь под вершинами равна AUC Манна–Уитни), `roc_points` — рабочие точки детекторов с не более чем двумя различными оценками (регулярки, ТЗ 3.1 «точка на ROC»). Общая сетка позволяет усреднять кривые сидов по вертикали.
- **A50. Смоук и тест.** Критерий приёмки «smoke.sh на скачанном и сгенерированном со всеми разделами отчёта» заставляет смоук открывать детерминированную голову тестового разбиения (200 документов на источник). Ни одна модель, гиперпараметр, регулярка или настройка конфига не выбиралась по числам `results/smoke/`; изменения конфига после смоука — только исполнительские ключи (A40).
- **A51. Процессы и память.** Оценка на полном размере: процесс сида E1 — 2–3,5 ГБ (первый сид с замером задержки трансформеров тяжелее), E4 — 1,2–1,5 ГБ, E3 после потоковой Bloom-подгонки — до ~1,5 ГБ; при ~13 ГБ доступной памяти без swap `--jobs 4` безопасен. Если процесс сида под `--jobs` падает, стадия падает, повторный запуск досчитывает только недостающие сиды; внутри каждой стадии `run_all.sh` действует errexit.
- **A52. Происхождение кода.** Раздел 2 отчёта перечисляет коммиты, на которых посчитаны результаты (`git_commits` сводок, `git_commit` файлов power/contract/verdicts); `check_acceptance` сравнивает разные коммиты результатов через `git diff --quiet A B -- src scripts configs`: коммит, меняющий только журналы или документы, считается тем же кодом. Между стадиями, пишущими результаты, изменения в `src/`, `scripts/` и `configs/` не коммитятся.
- **A53. Пин AgentDojo.** Пакет agentdojo==0.1.35 соответствует тегу v0.1.35 репозитория ethz-spylab/agentdojo, коммит a75aba7631d3ca5fb7ab938965c97ead2f9ff84b (проверено по локальному клону); записан в пины `fetch.sh`.
- **A54. Облегчённый смоук.** Смоук выполняет шаги 2–13 ТЗ на 1 сиде, 20 перемешиваниях, 200 документах на источник, 100 повторах бутстрепа, 20 эпизодах и 10 базах парафраз (ровно как в ТЗ); дополнительно в смоуке: 3 подвыборки на точку E2 вместо 10, части E6 без трансформерных (все атаки × позиции BIPIA, 512-токенные окна, FlyHash 40×), без замера задержки трансформеров и без повторного аудита контаминации на подвыборке. Эти части выполняются в настоящем прогоне; разделы отчёта в смоуке присутствуют, недостающие ячейки помечены «не выполнено в смоуке».
